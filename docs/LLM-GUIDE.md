# Подготовка процессов с помощью LLM

Работайте только с правилами, которые дал владелец процесса. Если неизвестны участник, условие ветвления, исход ошибки или связь, уточните их либо явно запишите неопределённость в описании. Не выдумывайте бизнес-правила ради успешной сборки.

## Рабочая последовательность

1. Прочитайте [JSON Schema](../schema/bpmnforge.schema.json), [поддерживаемый профиль](USER-GUIDE.md#формат-и-поддерживаемый-bpmn) и минимальный JSON в [README](../README.md). Установите BPMN Forge по README.
2. Подготовьте JSON версии 1: этапы, процессы, пулы, дорожки, узлы, связи и описания. Назначьте глобально уникальные стабильные ID; при изменении названия/описания сохраняйте ID. Не используйте `BPMNFORGE_` и свойства `Object.prototype`.
3. Выполните `npx --no-install bpmnforge validate "процесс.bpmnforge.json" --json` с теми же `--html`/`--bpmn`, которые будут у сборки. `validate` проверяет и геометрию.
4. Разберите JSON stdout. При коде 1 найдите элемент по `diagnostics[].id` и исправьте причину по `code`, учитывая `relatedIds` и координаты. Не меняйте бизнес-смысл без подтверждения. Код 2 требует исправления аргументов/путей, код 3 — исследования сбоя генератора. Повторяйте проверку до кода 0 и отдельно рассмотрите предупреждения.
5. Выполните `npx --no-install bpmnforge build "процесс.bpmnforge.json" --json`. Сохраните JSON как исходник для следующего изменения; HTML и `.bpmn` — производные файлы.
6. Откройте HTML через `file://` на 1440×900 и 1920×1080. Проверьте этапы, читаемость, вход в этап, описание блока, переходы, вызовы процессов, клавиатуру, панораму, масштаб, сетку и видимый логотип. Сверьте ID, участников, направления связей и BPMN с исходником. Если браузерная проверка недоступна, сообщите об этом прямо, не объявляйте её пройденной.

## Правила моделирования

- Используйте только типы и поля схемы. Не подменяйте неподдерживаемую BPMN-конструкцию похожей без согласования.
- Sequence остаётся в одном процессе и контейнере; message связывает разных участников. Неверную message-связь исправляйте по смыслу, не маскируйте association.
- XOR задаёт условия каждой исходящей ветви, кроме явно выбранной `defaultFlow`. AND не несёт условий/default.
- Каждый возврат/повтор явно помечайте `return: true`; граф без возвратных связей должен оставаться ацикличным. Не удаляйте возвраты для обхода проверки.
- `calledElement` указывает на существующий локальный процесс; общий процесс описывается один раз, циклы вызовов запрещены.
- Событийный подпроцесс имеет один уровень, условное начало и собственные внутренние связи. Для него обычно нужны полные bounds, включая детей, пулы и дорожки.
- Выбирайте `--layout auto` (без column/row — граф, с подсказками — сетка), `grid` для сетки или явный `graph` для пересчёта column/row только в памяти; при `CELL_CONFLICT`, `SHAPE_OVERLAP`, ошибках подписей/маршрутов исправляйте `column`/`row` или задавайте полную согласованную геометрию. Учитывайте ограничения из руководства пользователя.
- Пишите описания обычным текстом. Не вставляйте исполняемую разметку, внешние скрипты и небезопасные URL. Документы ищутся относительно выходного HTML; предупреждение `MISSING_DOCUMENT` требует проверки пути или объяснения отсутствия файла.
- Не редактируйте сгенерированные HTML/BPMN и не прячьте логотип viewer. Все изменения вносите в JSON либо код генератора, затем пересобирайте. Явные bounds и route сохраняются; не переписывайте их ради предупреждений без разбора причины.

## Читаемость и проверка компоновки

Оба режима используют профиль `readable-v1`: переменные ширины колонок, интервалы от границ фигур (предпочтительно 80, минимум 40), зазор рядов с подписями 40, маршрутов 14 и подписей 8. Сетка 20 выравнивает центры; `column`/`row` сохраняют логический порядок и пустые ячейки, а не старые абсолютные координаты. Широкая задача не расширяет все колонки этапа.

Соседство автоматических дорожек выбирается по sequence-переходам с приоритетом входных шагов. Принадлежность узлов и исходный порядок данных сохраняются; ручные bounds закрепляют авторское расположение.

В `readability` дополнительно проверяйте `profile`, `intervalDeviations`, `portExceptions`, `shapeClearances`, `readingFragments`, расстояния между границами подписи и владельца и `labels[].distanceToSource`. Подключение к грани ромба допустимо BPMN; предпочтение вершин — правило Forge. `READABILITY_GATEWAY_PORT_EXCEPTION` требует разбора степени и фиксированных препятствий, а не добавления нового шлюза. Явные `bounds`, `route`, `labelBounds` сохраняются при отклонении от профиля.

Выбор входов должен включать и межэтапные входы, и самостоятельные start. При масштабе 100–125% проверяйте видимость входа с подписью и непосредственного преемника, поля 32px и экранный текст от 14px. Фрагмент рассматривает до двух переходов. Для невместившегося преемника проверьте доступную кнопку «Далее» и диагностику фрагмента. Полоса дорожек 180px находится вне полотна; «Этап целиком» не зависит от удалённых обходов. Проверяйте сохранение камеры, режима и выбранного входа. При сравнении обязательно показывайте размеры схемы вместе с длинами, изгибами, пересечениями, зазорами и видимым контекстом.

Передавайте одинаковый `--layout auto|grid|graph` в validate/build. Источник остаётся JSON v1; ID, source/target, типы, условия и return не меняются при компоновке. Полная ручная геометрия приоритетна в auto. Graph использует только sequence без возвратов, сохраняет дорожки и этапы; выбранная длинная визуальная ось не означает главный бизнес-сценарий.

В JSON stdout проверяйте `readability`: режим, пересечения, близкие параллельные участки, длины, изгибы, подписи и декорации. `MANUAL_ROUTE_CLEARANCE` и `READABILITY_*` — рекомендации, а не ошибки BPMN; они не меняют код 0. Минимальный рекомендуемый зазор — 14; зона разведения у общего узла считается отдельно. Не скрывайте рост длины/изгибов при сравнении компоновок. Экспорт BPMN всегда содержит информационные связи; их переключатель действует только в HTML. Имена association видны через HTML-слой, без нестандартных полей BPMN DI.

В браузере проверяйте «Читать фрагмент», «Этап целиком», выбор входа, возврат к началу, сохранение камеры этапа, режим «Вся схема», переключатель приглушения, закреплённые дорожки, закрытие панели, отсутствие ссылок документов в HTML, входящие/исходящие переходы, монотонные +/−, колесо возле курсора и resize. Входной блок с подписью должен помещаться с полем минимум 32px. Не используйте `zoom ≥ 1,2` как замену проверке видимого текста и фрагмента. Проверяйте фактические размеры SVG-текста и логотип на обоих размерах окна.

## Ограничения автоматического выбора рядов

В `graph` сначала выбираются логические ячейки, затем физические интервалы, порты и маршруты. Предпочтительный ряд определяется по уже размещённым sequence-предшественникам той же дорожки и этапа; при их отсутствии используется ряд 0. Положение предшественника из другой дорожки в этом расчёте не учитывается. Узлы одного уровня сравниваются по предпочтительному ряду, затем по среднему ряду этих локальных предшественников. При равенстве выше размещается узел с более длинным оставшимся sequence-путём без возвратов; продолжение учитывается и за пределами текущего этапа. Окончательные равенства разрешаются по ID.

Это эвристика визуальной оси. Она может поставить короткую ветвь ниже длинной и создать пересечения, которых позволила бы избежать перестановка. Оценка «длина + 40 × изгибы + 400 × пересечения» сравнивает маршруты при выбранном размещении. До двух проходов улучшения перепрокладывают связи и выбирают порты; перестановки узлов по этой оценке сейчас не выполняются. Успешная валидация подтверждает допустимость геометрии, но не её оптимальность.

Изменение `row`/`column` в JSON не закрепляет узел в явном режиме `graph`: эти подсказки пересчитываются. Для авторского порядка ячеек используйте `grid`; точные `bounds` сохраняются в обоих режимах. Вертикальный порядок ветвей не задаёт важность или предпочтительность бизнес-исходов.

## Исследование геометрии

1. Сохраните текущие производные и отчёт как базу. Зафиксируйте режим, версию/коммит генератора и хеш исходника. Храните реальные процессы, документы, снимки и результаты в игнорируемой `private/`; в Git и пакет попадают только общие выводы и синтетические примеры.
2. Проследите причину размещения в коде: уровни графа, локальные предшественники, приоритет продолжения, занятость ячеек, ручные ограничения и назначенные порты. Разделяйте обязательное ограничение и выбор эвристики. Формулировку «генератор выбрал лучший вариант» подтверждайте фактическим сравнением вариантов.
3. Проверяйте одну гипотезу за раз. Для перестановки двух блоков сначала переместите только их; перенос связанного конечного события проверяйте отдельным вариантом. Сохраняйте ID, типы, участников, source/target, условия и `return`. Исследование выполняйте на отдельной копии JSON или изолированной копии генератора в `private/`, пересобирая HTML/BPMN. Контрольный запуск экспериментального генератора без изменения эвристики должен воспроизводить базовую геометрию.
4. После каждого варианта заново рассчитывайте маршруты и подписи. Сравнивайте локальные и глобальные пересечения отдельно, а также длины, изгибы, зазоры, размеры, исключения портов и предупреждения. Объясняйте появившиеся и исчезнувшие пересечения: улучшение фрагмента может изменить маршруты других этапов. При сравнении скорости сохраняйте медиану пяти сборок в одинаковых условиях.
5. Проверьте результат через `file://` на 1440×900 и 1920×1080, сохраните снимки нужной области и этапа целиком. Сверьте семантику экспортированного BPMN и хеш исходника. В отчёте разделяйте наблюдение, подтверждённую причину, результат эксперимента и предлагаемое исправление. Явно указывайте, внесено ли исправление в рабочий генератор или проверено только в эксперименте.

Выводы из конкретного процесса не превращайте в правило «всегда ставить ошибку выше» или «всегда оставлять успех на оси». Обобщённое изменение компоновщика должно оценивать допустимые варианты, сохранять подтверждённые правила процесса и проходить `npm test` с синтетическими регрессиями.

## Отчёт об изменении

Укажите изменённый исходник и сохранённые/новые ID, выполненные команды и коды завершения, предупреждения, пути обоих результатов и фактически выполненные визуальные проверки. Непроверенные бизнес-предположения перечислите явно. При изменении кода генератора выполните `npm test` по [локальной инструкции](RELEASING.md).
